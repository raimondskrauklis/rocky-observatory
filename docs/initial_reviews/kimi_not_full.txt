Verdict on the Game Platform Base Plan
Short version: This is an unusually disciplined document — better than most "platform" plans written by teams ten times the implied size. Its deferral lists, offline-first principle, and "reuse must be earned" policy are genuinely mature. But it has one strategic contradiction at its core, several silent feasibility gaps, and a few requirements that current tooling can't fully deliver as written. Below: what validates, then the devil's advocate pass, ranked by severity.
Part 1 — What holds up under scrutiny
Explicit deferral of Terraform, K8s, CDN, HA, multiplayer, payments. This is the strongest part. Most plans of this type fail by pretending scale problems exist. Naming what's out, and why it's not an architectural placeholder, is correct.
Untrusted-client principle, server-side validation of anything competitive/durable. Right, and stated early enough to shape the API.
Versioned release directories with a current symlink + one known-good prior release. Clean, atomic, reversible. Genuinely production-shaped.
Privacy/data-minimization baseline framed as questions to answer before launch rather than boilerplate.
Unity repo hygiene (Force Text, visible meta files, LFS patterns, ignored build dirs) — all correct.
Honest SPOF acceptance ("Droplet failure may require redeploy or restore... acceptable") with the compensating controls (backups, artifacts, runbooks) named. This is the right posture for a solo/small operator.
Reuse policy ("extract only after two games demonstrate the requirement") — architecturally humble and correct.
Part 2 — Devil's advocate pass
🔴 1. The launch stack contradicts the plan's own principles — this is the big one
The plan's Architectural Principles include "Avoid premature generalization" (§9) and "Keep simple paths simple" (§10). Then the Launch Capability list ships, on day one:
Keycloak — a JVM identity server with ~1,250 MB baseline RAM per instance and a 2 GB recommended container limit for small production deployments — for a game with no login, no accounts, and no feature that consumes identity. Player auth is explicitly deferred to "player account activation," which has no trigger date.
Redis + Celery worker + Celery Beat — three more containers — for which the only launch workload is "send a feedback email," which a synchronous endpoint does fine.
Four OAuth clients (observatory-web/mobile/api/admin) provisioned for surfaces that don't exist.
At launch, six of the seven application containers exist to serve one feedback form. And it's not free: Keycloak ships frequent security patches you must apply forever, realm upgrades need testing, and every idle service is a monitoring alert category that can page you for nothing. You cannot keep a service "implemented to production standard" (Principle 4) when nothing exercises it — production standard is earned by traffic, exactly as your own reuse policy says about APIs. The plan applies "reuse must be earned" to abstractions but exempts infrastructure from the same rule, with no justification.
Recommendation: keep the architecture fixed but change the deployment posture: ship launch with FastAPI + Postgres (+ optionally a single Redis for rate limiting). Deliver Keycloak/Celery/Beat as documented, tested, ready-to-enable recipes (compose profiles, realm import files, runbooks) that you activate when a real feature needs them. You lose nothing — enabling a recipe is hours of work — and you cut your day-one failure surface and ops load by more than half.
🔴 2. Unity WebGL is your riskiest decision, and the plan never budgets for it
A 10–15 minute atmospheric game delivered only via browser has hard constraints the document never mentions:
No managed threading — Unity Web builds are single-threaded; async patterns behave differently, and any System.Threading assumption dies. (Unity's own docs confirm this.)
Mobile Safari is a hostile environment: tabs get killed around ~500 MB RAM, and "a web game should launch within 10–20 seconds at most" before the watchdog kills it — with real-world reports of >50 MB builds failing to load on phones. Your plan has no build-size budget, no load-time budget, no device/browser support matrix, no memory budget, no loading-screen UX requirement. For a Blender-authored atmospheric 3D game with audio, blowing past these limits is the default outcome, not the exception.
Unity 6 Web builds are slow and flaky in CI — widespread reports of 30 min–2 h builds, LTO memory thrashing, and repeat-build failures. Your "Unity CI requirement" section assumes this is a solved checkbox; it is currently the single most likely thing to make your pipeline painful.
Strategic trajectory: WebGPU only became fully supported (out of experimental) in Unity 6000.6, and Unity positions it as the future; WebGL 2 is now the fallback API. Pinning "Unity 6 LTS" in 2026 should mean 6000.6+ to keep the WebGPU upgrade path open.
Recommendation: add a "Web Build Budgets" section: compressed download size target (e.g., ≤ 30 MB), time-to-playable target (e.g., ≤ 15 s on 4G), supported browser matrix (desktop-first; mobile explicitly in or out), and a CI build-time budget with cached Library/artifacts. And strongly consider shipping a desktop build (Windows/Mac) as a co-primary artifact — it's nearly free once the Unity project exists, and it hedges the entire WebGL risk class.
🔴 3. No capacity plan, no cost model
The plan names a single Droplet and co-locates Nginx, FastAPI, worker, Beat, Redis, and Keycloak — which per vendor guidance wants ~1.25–2 GB alone — plus expects managed PostgreSQL, Sentry, staging parity ("mirrors production"), versioned artifacts, and backups. No Droplet size is specified anywhere, and no monthly cost estimate exists. Realistically you're describing: 8 GB Droplet (≈$48/mo) × 2 environments + managed PG (≈$15–60/mo each) + Spaces + Sentry + domain ≈ $150–300/month before a single player exists. Not fatal — but a plan that claims production discipline should state it, and "staging mirrors production" is where the cost doubles.
🟠 4. The identity architecture has a hole you will fall into later
The diagram shows "Unity/Web client → Authorization Code Flow with PKCE → Keycloak." For a Unity WebGL build this is architecturally wrong as drawn: an OAuth redirect flow belongs to the browser page (your React shell), not inside the WebAssembly canvas. Doing auth inside Unity means popup/redirect juggling, token storage in the canvas's IndexedDB, and refresh-token handling nightmares. The standard pattern is: React performs PKCE, holds tokens, and passes short-lived access tokens into Unity via a JS bridge. The plan should say this now, because it determines client structure — getting it wrong means rebuilding the identity integration when it activates.
🟠 5. Your telemetry contract over-promises relative to tooling reality
"Did the game reach the main playable state? Did the player reach the ending? Which release version failed?" — Sentry's Unity SDK on WebGL cannot fully answer these: no line numbers on WebGL (IL2CPP unavailable), no native crash detection, sessions where the tab dies are only "Abnormal," and the crash-free session rate "will show 100%," plus open issues about events not being sent from WebGL builds. Sentry is a good error tracker; it is not a funnel. Reaching "playable state" and "ending" requires bespoke, privacy-minimal telemetry beacons (version-stamped events to your own API) — which is fine and fits your privacy posture, but it must be designed explicitly, not implied to fall out of Sentry. (Positive: DigitalOcean Uptime checks — which are a separate, ~$1/mo product, not part of "DigitalOcean Monitoring" as the plan implies — do cover the external HTTPS availability requirement.)
🟠 6. Celery-on-Redis correctness details are missing
The plan says "durable task effects must be idempotent" — good — but idempotency doesn't help if the task is never delivered. With Redis as broker you must specify: appendonly yes + appendfsync everysec (otherwise tasks die with the last RDB snapshot), a maxmemory policy that never evicts keys (allkeys-lru silently eats your queue — a documented Celery caveat), task_acks_late, and visibility_timeout tuned against your longest task (default 1 h; tasks exceeding it execute in an infinite redelivery loop). There's also a known Celery bug class where workers stop consuming after Redis reconnects. None of this is in the plan. Also note the common advice to separate broker Redis from cache Redis — your single Redis container is both, so a memory-pressure event takes out rate limiting, cache, and the queue simultaneously.
🟠 7. Secrets, deploy path, and Keycloak config-as-code are unspecified
"Store secrets outside the repository" — in what? DigitalOcean has no secrets manager. Unencrypted env files on the Droplet? That needs saying, plus rotation mechanics, plus how CI obtains deploy credentials and where the deploy runs from ("self-managed build/deploy workflow" is doing a lot of unexplained work).
Realm configuration: Keycloak realms/clients/flows configured by hand in two environments, with Terraform explicitly out of scope and no keycloak-config-cli or equivalent mentioned = guaranteed staging/prod drift and un-reproducible identity — a direct violation of your own "reproducible builds" principle. You don't need Terraform; you need some declarative realm import in the repo.
CI license activation requires your Unity account email, password, and 2FA/TOTP key in CI secrets (personal-license manual activation was withdrawn by Unity; automation needs the authenticator key). Those secrets grant full account access and must be in the secrets register the plan demands but doesn't populate.
🟡 8. Operational ownership is a list of questions with no answers
Eleven ownership questions, all unanswered, for what appears to be one person. "Production-grade" implies an on-call reality: Sentry triage, patch cadence for Keycloak/FastAPI/Unity, restore drills "periodically" (which, unscheduled, means never), dependency updates. This is the plan's quietest risk: not technical — sustainability. Add a realistic SLA ("best effort, 48 h"), a monthly ops checklist with owners, and a restore-drill calendar entry, or the monitoring stack becomes alert theater.
🟡 9. Smaller but real gaps
No milestones. A platform plan with zero timeline invites the classic failure: six months of infrastructure, no playable game. Add ordering: playable build on staging by date X; everything else sequences after.
No release retention/cleanup policy for /srv/releases — disk grows forever.
Staging tester access unspecified (Nginx basic auth?).
Landing page as React SPA hurts SEO/perf for a marketing surface; a static/SSR landing with the React app only where interactivity needs it would be simpler and faster.
Egress risk: a viral post × a 30–80 MB game × no CDN can saturate one Droplet's bandwidth. Accepted-risk is fine; unquantified accepted-risk is not.
Feedback spam/abuse: rate limiting is mentioned, but no CAPTCHA/proof-of-work for a public form.
Local saves in WebGL live in IndexedDB — clearing browser data wipes progress. Fine for a short game, but the privacy section should say save-data is device-local and losable.

Done — game-platform-review-kimi.md is written (~2,200 words). Here's how your three points shifted the review, plus the advice you asked for:
On "capacity is the actual value" — I partially retracted the idle-infra criticism, but with a sharp distinction: you don't learn from running services, you learn from exercising them. A Keycloak with zero clients teaches you how to keep a Keycloak alive — not the skill you said was valuable. So the file proposes a Capability Curriculum (§1): six scheduled sprints (restore drill, rollback executed once, staging-only Keycloak + PKCE, chaos drill with key rotation, Celery kill-the-worker test, incident tabletop). You keep 100% of the learning, get drill logs as evidence, and cut launch cost ~40–60%. A middle path if you want reps immediately: run the full stack on staging from day one — 90% of the practice, 0% player-facing blast radius.
On "Keycloak/Postgres are later / I master them" — one correction: Postgres stays from day one regardless (the feedback API needs a durable store, and managed PG is your cheapest component). The deferral candidates are Keycloak, Celery, and Beat — and mastery removes the "can you do it" question, not the "should it run 24/7 for zero users" one. Unpatched public-facing Keycloak is a liability to future players, not to your skill set.
On web-first as the direction — validated, but this upgrades the WebGL budgets from red to red-critical: they're now product requirements, not engineering niceties. Also pin Unity 6000.6+ (WebGPU path), SSG the landing for discoverability (monetization needs search traffic), and note CI Unity builds are your most likely pipeline pain point.
Alternative approaches since you're pre-implementation (§5, cheap now / expensive later):
itch.io as a parallel channel — self-hosting stays canonical (it's the educational point), but itch gives real players and rehearses distribution, which the plan currently ignores
PWA early — service-worker caching serves your load-time budget and pre-builds mobile skills
Own beacon telemetry instead of deferring analytics wholesale — covers "reached playable state / reached ending" without any third-party stack
Spaces named explicitly for artifacts + pg_dump exports
A ?smoke=1 build mode that auto-plays to the playable state and beacons success — enables CI + post-deploy verification
One-page Unity-vs-Godot ADR — Godot's web exports are smaller/faster; documenting why Unity wins prevents a mid-project crisis of faith
And the three edits that matter most if you do nothing else: (1) add the Web Build Budgets section, (2) swap day-one Keycloak/Celery/Beat for ready-to-enable recipes, (3) date one milestone — playable build on staging — before any other infrastructure work.
